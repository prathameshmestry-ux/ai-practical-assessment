# Code Review Notes
## AI-Assisted Review Summary  
AI-assisted review confirmed the project follows a sound AEM Cloud Service design: servlets handle HTTP only, TicketServiceImpl owns ticket and comment logic, data is stored under /var/ai-practical-assessment/tickets, and UI pages stay under /content/ai-practical-assessment/support-tickets/. Shared helpers like ServletAuth and TicketApiJson keep auth and responses consistent, and TicketStatusTransitionValidator enforces the status workflow cleanly. Review also highlighted areas to improve: stronger server-side assignee checks, broader automated tests for update/comment/status flows.
## My Review Observations
From manual review, the codebase is readable, modular, and aligned with AEM patterns already used in the project. Backend changes use a service user for writes, bounded list/search queries, and clear servlet responsibilities; frontend changes deliver the required ticket create, dashboard, detail, comment, and status experiences without unnecessary page reloads. Test coverage is good for core rules like status transitions and search predicates, but less complete for full ticket lifecycle automation and some logged-in UI scenarios, which were mostly validated through quickstart and local AEM testing.
## Changes Made After Review  
Several review findings were addressed during implementation. ACLs were added for the ticket-service user, JSON request parsing was fixed, the status control was rebuilt for async in-place updates, and authentication was changed to component-level gating with servlet 401 responses for anonymous API access. Supporting fixes included dashboard table styling, correct page and component placement, integration test query parameter handling.
## Suggestions Rejected (and why)
Rejected: `/content` ticket storage, commons-io, page-level auth redirect, contains-search, external DB, role-based ACL, Jackson, server assignee validation (v1), full E2E, tickets as cq:Page, email notifications, and shared JS helper — mostly wrong AEM pattern, out of v1 spec scope, unnecessary dependencies, or refactor-only with no functional gain for this assessment.
